# RunTrace v0.2.0

Published on 2026-08-17 through PyPI Trusted Publishing. The package is
available from [PyPI](https://pypi.org/project/ml-runtrace/0.2.0/), and the
corresponding [GitHub Release](https://github.com/Corvus-226/RunTrace/releases/tag/v0.2.0)
points to the reviewed `v0.2.0` tag.

RunTrace v0.2.0 adds an atomic snapshot-before-execution command and richer,
privacy-conscious provenance for Python packages installed from direct sources.

## Highlights

- Run `ml-runtrace run -- COMMAND...` to save a snapshot before starting an
  experiment and return the child process's exit code.
- Preserve the exact command argument vector as well as a readable command,
  without inserting an implicit shell.
- Capture sanitized PEP 610 provenance for VCS, archive, and local-directory
  installations, including resolved VCS commit IDs and archive hashes when
  available.
- Inspect exact arguments and direct-package origins with `show`, and compare
  them deterministically with `diff`.
- Present RunTrace on GitHub and PyPI with the original experiment-fingerprint
  project hero.

## Install or upgrade

Install the `ml-runtrace` distribution from PyPI, then use the collision-free
`ml-runtrace` command or `ml_runtrace` Python module:

```console
python -m pip install --upgrade ml-runtrace==0.2.0
ml-runtrace --version
python -m ml_runtrace --version
```

RunTrace v0.2.0 supports Python 3.10, 3.11, and 3.12 on Windows and Linux.

## Snapshot before running an experiment

From an initialized Git repository with at least one commit:

```console
ml-runtrace run --name baseline --config configs/train.yaml -- python train.py --config configs/train.yaml
```

The `--` separator ends RunTrace options. Everything after it is passed to the
child process as an exact argument vector. RunTrace writes the snapshot before
the child starts. If capture fails, the child is not started; if the child
fails, the snapshot remains stored and its exit code is returned.

RunTrace does not insert a shell. Pipes, redirection, variables, and other shell
syntax are interpreted only when a shell is explicitly chosen as the child
command.

The original `ml-runtrace snapshot` command remains record-only and does not
execute the value supplied through `--command`.

## Direct dependency provenance

Snapshots now read standardized `direct_url.json` metadata for distributions
installed from version control, an archive, or a local directory. VCS records
can include the VCS type, sanitized repository URL, requested revision,
resolved commit ID, and a safe relative package subdirectory. Archive records
can include a sanitized URL, available hash, and safe relative subdirectory.
Local-directory records retain only whether the installation is editable.

URL credentials, queries, fragments, unsafe subdirectories, and local absolute
paths are omitted. Remote hosts, repository paths, revisions, and safe relative
subdirectories can still identify private projects, so review snapshot YAML
before sharing or committing it.

## Compatibility

The snapshot schema remains version 1. New fields are additive and defaulted,
so v0.2.0 can load snapshots written by v0.1.0. Older v0.1.0 installations may
reject v0.2.0 snapshots containing the new fields; upgrade before reading those
records.

The distribution remains `ml-runtrace`, the import remains `ml_runtrace`, and
the only console command remains `ml-runtrace`. No `runtrace` import or command
alias is provided because those names belong to an unrelated PyPI project.

## Known limits

- RunTrace records reproducibility context; it does not track metrics, host a
  dashboard, schedule jobs, or store model artifacts.
- GPU and CUDA detection is best-effort and currently targets NVIDIA tooling.
- Direct-package provenance depends on valid PEP 610 metadata supplied by the
  package installer.
- Stored snapshots are local files; teams choose whether to ignore, archive,
  or review and commit them.
